# 模型精度验证报告

**项目：** 本地检索系统 — Embedding Engine
**评测范围：** BERT 文本-文本检索（NQ数据集）与 MobileCLIP 多模态检索（COCO数据集）

---

## 1. 总结

本次验证针对接入 `EmbeddingEngine` 的两个模型，分别使用 NQ 和 COCO 数据集的100条样本子集，跑标准检索评测基准，结果如下：

| 模型 | 任务 | 数据集 | Recall@1 | Recall@5 | Recall@10 | MRR |
|---|---|---|---|---|---|---|
| BERT | 文本 → 文本 | Natural Questions (NQ) | 14.00% | 28.00% | 34.00% | 0.2205 |
| MobileCLIP | 文本 → 图片 | COCO | 64.00% | 88.00% | 99.00% | 0.7518 |
| MobileCLIP | 图片 → 文本 | COCO | 66.00% | 93.00% | 98.00% | 0.7764 |

**核心结论：** MobileCLIP 的多模态检索表现良好，且双向结果一致、稳定。BERT 的文本-文本检索表现明显偏弱，低于BERT系模型在检索类任务上通常应有的水平——这更可能是模型/池化策略配置的问题，而不是整个检索流程存在缺陷。

---

## 2. 评测方法

### 2.1 数据集

| 数据集 | 任务 | 样本量 | 候选池大小 |
|---|---|---|---|
| Natural Questions (NQ) | 问题 → 答案段落检索 | 100 | 100 |
| COCO | 图文双向检索 | 100 | 100 |

注：候选池只有100条时，Recall@10 的随机基线（瞎猜）本身就有10%。解读结果时应参照这个基线，而不宜直接跟公开论文里动辄1000~5000条候选池规模的基准数字做横向对比。

### 2.2 流程

1. 所有向量均通过 `EmbeddingEngine` 生成：
   - BERT路径：`generateTextEmbeddingWithMode(text, mode: TextEmbeddingMode.bert)` → 768维向量
   - MobileCLIP路径：`generateTextEmbeddingWithMode(text, mode: TextEmbeddingMode.mobileClip)` / `generateImageEmbedding(imageBytes)` → 512维向量，共享同一语义空间
2. 通过 `cosineSimilarity` 计算query与所有候选项之间的两两余弦相似度。
3. 按相似度对候选项排序，与已知的正确配对做比对，计算 Recall@1/5/10 与 MRR。

### 2.3 指标说明

- **Recall@K**——检索结果前K名里，能否命中正确答案，命中记1、未命中记0，取所有查询的平均值。
- **MRR（平均倒数排名）**——正确答案排第几名，取倒数再求平均。正确答案排第1名贡献1分，排第2名贡献0.5分，排第10名贡献0.1分，越接近1说明正确答案平均排位越靠前。

## 3. 结果详情

### 3.1 NQ —— BERT 文本-文本检索

```
样本量    : 100
Recall@1  : 0.1400 (14.00%)
Recall@5  : 0.2800 (28.00%)
Recall@10 : 0.3400 (34.00%)
MRR       : 0.2205
```

**观察：** Recall@10 为34%，在当前候选池规模下只是随机基线（10%）的约3.4倍。即使考虑到候选池较小这一因素，这个数字依然明显低于BERT系模型在检索类任务上通常被期望达到的水平。

### 3.2 COCO —— MobileCLIP 多模态检索

**文本 → 图片**

```
Recall@1  : 0.6400 (64.00%)
Recall@5  : 0.8800 (88.00%)
Recall@10 : 0.9900 (99.00%)
MRR       : 0.7518
```

**图片 → 文本**

```
Recall@1  : 0.6600 (66.00%)
Recall@5  : 0.9300 (93.00%)
Recall@10 : 0.9800 (98.00%)
MRR       : 0.7764
```

**观察：** 两个方向的表现都很强，且高度对称（双向Recall@1相差不到2个百分点），符合一个运作良好的共享向量空间应有的特征。这个结果也在预期之内——CLIP系模型的训练目标本身就是图文对比学习，本次评测相当于是在测试模型的"本职任务"。

---

## 4. 原因分析

### 4.1 MobileCLIP：表现符合预期

- Recall/MRR 指标强劲、且双向结果一致，说明tokenizer、TFLite推理链路、以及经过L2归一化后的余弦相似度计算，整条流程端到端运作正常。
- Recall@10 接近满分（98%~99%）在一定程度上是候选池仅100条这个规模带来的"天花板效应"，不宜直接与公开的MobileCLIP/CLIP论文基准数字对比（那些基准通常用1000+条候选池）。相比之下，Recall@1 对候选池规模的敏感度低得多，更能反映真实水平，64%~66%是一个合理的结果。

### 4.2 BERT：低于预期——可能原因

NQ的结果偏弱，更可能是模型/配置选择的问题，而不是检索或推理流程本身的缺陷（MobileCLIP的结果已经证明共用的 `cosineSimilarity`/排序逻辑本身是正确的）。按可能性从高到低排列：

1. **未经微调的原生BERT向量。** 原生BERT（只用掩码语言模型和"下一句预测"两个训练目标训练出来的）产出的句向量，是业内已知会在向量空间里聚集在一个狭窄的各向异性区域，导致余弦相似度普遍偏高、区分度差。而专门针对句子相似度/检索任务微调过的模型（如Sentence-BERT、DPR系列编码器），在这类任务上通常会显著优于原生BERT。
2. **池化（pooling）策略。** 如果句向量目前是单纯取 `[CLS]` token的输出，改成对所有token向量做平均池化（mean pooling），往往能带来明显的检索效果提升。
3. **任务/领域不匹配。** NQ数据集是"较短的问题"去匹配"较长的答案段落"，这是一种非对称检索任务，原生BERT本身并不是针对这种任务优化的。

### 4.3 不代表流程存在bug

由于MobileCLIP这条路径——同样共用 `EmbeddingEngine`、`cosineSimilarity`、排序逻辑——表现良好，可以判断BERT的短板出在BERT模型本身/预处理配置上，而不是共享的检索基础设施出了问题。

---

## 5. 建议

| 优先级 | 建议 |
|---|---|
| 高 | 评估换用一个专门针对检索任务微调过的BERT变体（如Sentence-BERT/DPR系列的checkpoint），替换当前的原生BERT模型，并重新跑一遍本次基准测试。 |
| 中 | 确认（如有需要则调整）当前的池化策略，从"仅取 `[CLS]`" 改为在 `TextEmbeddingService`/`TextPreprocessor` 中使用平均池化。 |
| 中 | 用更大规模的候选池（≥1000条样本）重新跑两组评测，以获得能跟公开基准直接对比的结果，同时也能减少目前MobileCLIP Recall@10上出现的"天花板效应"。 |
| 低 | 之后每次报告指标时，注明当前使用的是100条样本这个规模，避免和标准基准数字产生误导性对比。 |
